# CaerdonWardrobe - Development Notes

Reference detail per area: the rule, why it is that way, and what has or has not been seen in game. Not loaded automatically; `CLAUDE.md` holds what every session needs and points here.

Keep entries short and factual. No session narration, quotes or test counts. "Offline" means run under LuaJIT with a mocked client, which checks logic and not the client. "Author" is the addon's author; a date is when something was decided or observed.

## WoW Forever Client

- **Identity:** game type `camelot` (alias `forever`), `WOW_PROJECT_ID == WOW_PROJECT_CAMELOT` (18), `## Interface: 16001`. `CaerdonAPI:IsForeverClient()` / `GetClientFlavor()` are for reporting only.
- **Version gates:** `select(4, GetBuildInfo())` is `16001`, so `tocversion >= 110000` is false. Housing is correctly gated off this way (Blizzard_Housing* is `AllowLoadGameType: standard`).
- **TOC gating:** `## AllowLoadGameType` and per-file `[AllowLoadGameType camelot]`. `mainline` includes camelot, `standard` is retail only. Overrides live in `Camelot/` subfolders.
- **Not loaded:** Blizzard_EncounterJournal (standard / classic only), Blizzard_GarrisonUI, Blizzard_Housing*, Blizzard_ExpansionTrial. The EncounterJournal and Mission features wait for `ADDON_LOADED`, so they stay dormant.
- **Mail:** `InboxFrame:Update()` and `OpenMailFrame:UpdateButtonPositions()` replace the retail globals; `SendMailFrame_Update` is still global. `features/Mail.lua` hooks whichever exists.
- **Bank:** `CamelotBankPanelItemButtonMixin:Refresh()` calls through `BankPanelItemButtonMixin.Refresh(self)`, so the table hook still fires.
- **Events:** `UPDATE_EXPANSION_LEVEL` is undocumented and registered via `pcall`. All other registered events exist in Forever's event documentation. In the client (1.60.1.70938) it registers without an error, as do the five talent events the core also registers through `pcall`.
- **Seen in the client by the test addon (1.60.1.70938, 2026-11-15; one or two toons, so a fact about what was looked at):**
  - Tooltip lines: the binding line (type 20) carries `bonding`; the slot line (21) `isValidInvSlot` and `isValidItemType`; a requirement line (43) `usable`, `requirementType` and `level`; use and equip effect lines (44, 45) `spellID`; the sell price line (11) `price`; the name line (22) `quality`. The tooltip data has `dataInstanceID`, `guid` and `id`.
  - `C_PlayerInfo.CanUseItem` knows the classic armor proficiency: false for mail (Soldier's Wristguards 6550) on a level 29 hunter who meets its level.
  - `C_TransmogCollection.GetCategoryAppearances` follows the wardrobe's filter, and "Not Collected" is off by default, which is why the wardrobe shows collected looks only. With it on, uncollected appearances are returned (Chest: 56 of 452 collected).
  - No secret value in the item, container, tooltip or transmog answers out of combat.
  - `ReloadUI()` called from an addon's click handler or slash command reloads the UI. Called from a timer, with no click or key press behind it, it is refused (`ADDON_ACTION_BLOCKED`, function `Reload()`), so addon code cannot reload by itself.
  - `C_AddOnProfiler.IsEnabled()` is true with no setup.
  - Retail (12.1.5.70783, one toon) showed the same for the tooltip line fields, the secret values, the reload, the profiler and the events, and `GetCategoryAppearances` returned 33,386 uncollected appearances of 41,615.
  - Items from later expansions: `C_Item.DoesItemExistByID` is true for one item each from The Burning Crusade to Legion, but their data never loads. The function proves nothing, and such items cannot stand in as test items.
- **Specializations:** none. `GetSpecialization`, `GetSpecializationInfo` and `GetSpecializationInfoByID` do not exist (only `C_SpecializationInfo.*`, `GetLootSpecialization`, `GetSpecializationInfoForSpecID`). Use `CaerdonAPI:GetPlayerSpecializationIndex()`, `GetSpecializationInfo(index, ...)`, `GetSpecializationInfoByID(specID)`, `GetLootSpecializationID()`; they return nil without a spec system.
- **Talent trees:** one trait tree per class in three groups. `CaerdonAPI:GetTalentTrees()` reads them as Blizzard's Camelot talent pane does: `C_SpecializationInfo.GetCombatConfigIDForSpecGroup(GetActiveSpecGroup())`, `C_Traits.GetConfigInfo(configID).treeIDs[1]`, `C_Traits.GetGroupDisplayInfoByTreeID` (names, order), `C_Traits.GetGroupCurrencyInfo` (`currencyInfos[1].spent`; a missing group is 0). `GetPrimaryTalentTree()` returns the leader, nil on a tie or with nothing spent. Retail has neither group function, which is the feature gate. Cached until `InvalidateTalentTrees()`; `CaerdonWardrobeMixin:OnTalentsChanged` (trait and talent events, coalesced over 0.5 s) refreshes only when the leading tree changed.
- **API coverage (Forever 1.60.1 docs):** every documented API the addon uses exists; `TransmogUseErrorType` values match retail. Undocumented calls that Blizzard's camelot-loaded code also uses (toy, heirloom, pet journal, black market, merchant / loot / quest link getters) are safe. `C_TradeSkillUI.GetAllRecipeIDs` and `GetRecipeFixedReagentItemLink` are not referenced in Forever's UI code, so they are guarded.
- **Ranged slot:** `GetInventorySlotsForType` in `types/EquipmentMixin.lua` sends `INVTYPE_RANGED` / `RANGEDRIGHT` / `THROWN` / `RELIC` to slot 18 when `C_PaperDollInfo.IsRangedSlotShown()`. Without it bows were compared against the melee weapon.
- **Professions:** every profession has one child skill line with the parent's name ("Mining" 186 > "Mining" 2946), and secondary professions cache no parent skill level, so `CaerdonProfessionData[realm][toon]["Cooking"]` can be a bare `{ childSkillLines = ... }`. `CaerdonRecipe:GetPlayerSkillInfo` checks the top-level entry and every same-named child and keeps the highest. `GetProfessions()` returns prim1, prim2, first aid, fishing, cooking. `select(7, GetProfessionInfo(index))` returns base skill lines (seen: Herbalism 182).
- **Recipe tooltips:** "Requires Cooking (40)" is a `UsageRequirement` line (`requirementType` Skill). A non-red line is the client's verdict that the rank is met and overrides the cached rank; a red line uses the cache to tell "rank too low" (`lowSkill`) from "no profession". Recipe items report a generic "Learning" spell, so the name-based `GetRecipe` lookup identifies the recipe.
- **Collections:** the wardrobe UI hides uncollected appearances and transmog is restricted to same-type items, but the `C_TransmogCollection` APIs are unchanged.

## Client Sources

Two public mirrors cover both flavors. The clones live outside the addon folder, in `~/Projects/WoW/Builds/` (`source/<flavor>`, `resources/<flavor>`); `update.sh` in that folder creates or refreshes them. Neither belongs in the repo.

- **Blizzard's Lua and XML:** `git clone --depth 1 --branch <branch> https://github.com/Gethe/wow-ui-source <dir>`, with `live` for retail and `forever` for Forever (`ptr`, `ptr2` and `beta` exist too). `version.txt` and the commit subject name the build. `Ketho/wow-ui-source-forever` carries the same `forever` commit.
- **Listings:** `Ketho/BlizzardInterfaceResources`, branches `live` and `forever`, folder `Resources/`: `GlobalAPI.lua` (every global function, documented or not), `Events.lua` (the documented events only), `LuaEnum.lua`, `GlobalStrings/enUS.lua` (other locales beside it), `FrameXML.lua`, `Mixins.lua`, `Frames.lua` (global frames, including the ones the client creates itself), `WidgetAPI.lua` (the methods of each widget type). It is large, so clone with `--depth 1 --filter=blob:none --sparse` and then `git sparse-checkout set --no-cone` the files needed. In Git Bash set `MSYS_NO_PATHCONV=1` for that command, or the leading-slash patterns are rewritten to Windows paths and nothing is checked out.
- **Previous builds are kept.** `update.sh` tags each build it fetches as `build/<version>` in that clone, and an update never drops an older tag. `update.sh changes [path]` summarises the two newest; `update.sh deepen [N]` fetches N earlier builds from the mirror's history. For anything else: `git -C source/<flavor> diff build/<old> build/<new> -- <path>`, or `git show build/<old>:<path>` to read one old file. After a client patch, read that diff for the Blizzard addons the features hook before trusting them.
- **The installed client** can export its own code (`ExportInterfaceFiles code` in the login-screen console, started with `-console`) into `BlizzardInterfaceCode/` under the flavor's folder. That is the only source guaranteed to match the installed build, but it is a manual step for the author, so it is the exception: ask for one only when a specific build is needed and no mirror has it (the listings mirror can trail the source mirror by a build). Move the result to `~/Projects/WoW/Builds/exports/<flavor>-<build>/` instead of reading it in the game folder, and keep older exports there for comparison.
- **Pitfalls when reading the mirrors:**
  - The API documentation folder lists a function for both flavors even when its Blizzard addon is not loaded on one (housing events exist in Forever's listing). Presence in a listing means the client knows the name, not that the feature works.
  - A Blizzard addon folder can hold several TOC files (per game family); read the one for the flavor before concluding what loads.
  - A tooltip line's fields (`bonding`, `isValidInvSlot`, ...) are not in the documentation for either flavor. Only an in-game dump shows which exist.
  - A name both clients have although neither listing does may be a Lua fallback. `Blizzard_Deprecated` (loaded by both flavors) defines old names such as `Enum.HousingCatalogEntrySubtype` and wraps changed functions so they still return the old fields, as long as the CVar `loadDeprecationFallbacks` is on and until Blizzard deletes the file. "Missing from both listings" is therefore a reason to look for a definition, not a verdict, and "the client has it" is no reason to keep using it.
  - Other addons recreate removed globals (GearQuestForever defines `GetItemCount` and `GetItemFamily`), so a fallback to a legacy global can end up running another addon's function.
- **After a client patch** run `update.sh`, then the static check (next section), then read `update.sh changes` for the Blizzard addons the features hook: the check proves a hooked name still exists, not that it is still called the same way.

## Static Check

`luajit tools/static-checks.lua` compares the names the addon uses with what each client has, using the mirrors above (`--builds DIR` or `$CAERDON_BUILDS` when they are elsewhere; `--verbose` adds what each client does not load; `--emit-facts` is below). It is offline evidence: it reads code and listings and runs no client. Exit code 1 means findings, 2 a problem with the setup. `tools/` is not packaged (`.pkgmeta`).

- **Checked per client:** every global the addon reads; every function of a `C_*` or Lua namespace, `Enum` / `Constants` value and method of a global frame or mixin it names; every event it registers or names a handler after; every global string; every literal `hooksecurefunc` target. And, once: every global it writes.
- **"The client has it" means** a listing names it or Blizzard code *that client loads* defines it. The loaded files are worked out per flavor from the TOCs (`AllowLoadGameType`, `ExcludeLoadGameType`, `AllowLoad`, the `[Family]` and `[Game]` folders): retail answers to `mainline` and `standard`, Forever to `mainline` and `camelot`. So Forever gets no credit for the Encounter Journal, which is in its tree but never loads. That Blizzard's code merely reads a name is no proof either: it reads other game types' globals behind guards.
- **Globals come from bytecode** (`jit.util`), the addon's and Blizzard's alike, so scope is the compiler's verdict and a comment or string cannot confuse it. A field is followed through a local that holds the global (`local api = C_Container`).
- **Frames** are resolved through XML, including a template's `$parent` children (`MerchantItem1ItemButton`); their methods through `mixin`, `inherits` and `CreateFromMixins`, then the widget listing.
- **Events:** the listing is incomplete, so an event Blizzard's own code registers by name counts as known too, the login screens' code included.
- **The allowlist** (`tools/static-checks-allow.lua`) holds four kinds of claim: global writes that are intended; other addons' globals; names both clients have that no source shows (accepted only while Blizzard's loaded code reads them); and names only one client has, or neither, each with the guard that keeps the code off it. An entry that stops applying is itself a finding. Read the code before adding one, because an unguarded use of a missing name is a bug. Entries are per name, so a name with one guarded and one unguarded use stays a finding until the unguarded one is fixed.
- **Deprecation fallbacks** are a finding of their own kind. A name `Blizzard_Deprecated` defines counts as there, and every such name the addon uses is listed with the file that defines it, until the code moves to the new API or the allowlist's `deprecated` table says why it may stay. A wrapped function exists natively as well; the wrapper only adds the old fields to its answer, so the question for each call is whether the addon reads one of those.
- **Blind spots:** names built at run time (`_G["MerchantItem" .. i]`), methods on a local or on a child reached through `parentKey`, fields of a frame that are not methods, other addons' code, locales other than enUS, and whether a function that exists in both clients behaves the same in both.
- **The header names the builds used.** The listings mirror can trail the source mirror by a build; a finding that depends on the gap is settled in the client.
- **The test addon is read too** (`CaerdonWardrobe_Tests`, listed in `ADDON_ROOTS`), with untracked files included, so a new file is checked before its first commit. A hook on the addon's own frame is not a finding.
- **`--emit-facts`** writes two generated files, neither tracked. `CaerdonWardrobe_Tests/ApiNames.lua` is every name of the client the addon reads, which the test addon's recorder hooks (section Offline Harness). `CaerdonWardrobe_Tests/StaticFacts.lua` holds the check's conclusions: every name and event that is not in both clients, every literal hook target, and the Blizzard addons each client loads or never loads. The test addon compares them with the client (next section). Both depend on the code and the second on the builds in the mirrors; a working copy without them only makes those contracts skip and the recorder refuse. They are compared as text, so a run without the option reports one that is out of date: emit again after any change to the names the addon uses and after `update.sh`.

## Test Addon

`CaerdonWardrobe_Tests/` is a second addon in the repository, for development only. It depends on the addon, runs in both clients through a junction of its own in each `AddOns` folder, and is not packaged (`.pkgmeta`). What it records was seen in a client. Its own logic has been run offline against a mocked client; that says nothing about the client.

- **Out of the game:** its saved variables, `CaerdonWardrobeTestsDB`, which the client writes on `/reload` and on logout. `luajit tools/test-results.lua [--wow DIR] [section ...]` prints them for every account of both clients (`$CAERDON_WOW` for the folder that holds `_retail_` and `_forever_`; `detail` or `contract:<id>` for a contract's stored detail).
- **Into the game:** `Plan.lua` holds the standing defaults; `Plan.local.lua` is loaded after it and is not tracked. One-off requests go there: `probeItems` (item IDs whose client facts, tooltip lines and verdict are recorded after login), `skip`.
- **In game:** `/cwtest` opens a small window; `/cwtest help` lists the commands. After login, once the addon's queue is empty, every test that has to run runs by itself, out of combat.
- **Contracts** (`Contracts.lua`) are facts about the client: a result is kept per build and a contract with a final result (`pass`, `fail`, `info`) does not run again. `skip` means a precondition is not met on this toon, `manual` that the author has to do something. Bump a contract's `version` when it checks something else.
  - `static.names`, `static.hooks`, `static.events`, `static.addons` ask the client what the static check concluded. A name the check calls missing that exists in the client means the check's model is wrong and fails the contract. A name it expects that is absent is only listed: its Blizzard addon may load on demand. A global another addon created (`issecurevariable`) is listed apart. `static.names` also lists which deprecation fallbacks are present, with the CVar's value.
  - `shape.*` check the fields the addon reads off the item, container, tooltip and transmog answers. `tooltip.lineFields` collects every field seen on a tooltip line, per line type, and adds to it on each login. `secrets.itemData` looks for secret values in those answers, out of combat.
  - `reload.click`, `reload.slash`, `reload.timer` say whether addon code may call `ReloadUI()`. A note is left in the saved variables before the call: finding it after the reload is the pass, still running two seconds later the fail. For `reload.timer` a refusal is recorded as `info`: it asks whether a click is needed, and "yes" is an answer. Blizzard's own UI calls the plain `ReloadUI()` from click handlers in both flavors, and `C_UI.Reload` is documented without a restriction.
  - `transmog.categoryAppearances` switches both wardrobe filters on for the reading and puts them back: `GetCategoryAppearances` follows the filter.
  - `canary.knownItem` reads what the client says about one plain item (Brawler's Harness 6125: its item info, its appearance and source, the source's fixed fields) and compares that with the reading of the newest earlier build the results still hold. It carries no expected values, so it holds for either client: a first reading is `info`, a difference is a `fail` that names the field. What depends on the toon or the collection (which fields a source has, whether it is collected) is kept beside the reading and not compared.
- **Verdict tests** (`Verdicts.lua`, the cases in `VerdictCases.lua`) check the addon's status for an item on a named kind of toon. They test the addon's code, so they run on every login.
  - A test names a shape (the raw client facts that define the case), a pool of item IDs and the expected status. The facts are read by `Facts.lua` straight from the client, never from the addon's own processing, and are stored next to the verdict.
  - Same facts, other verdict: `regression`. An item that no longer fits the shape is `retired` with the fact that moved, and the next pool item that fits takes its place; no item left is `uncovered`.
  - The expected status is written by hand from the rule in these notes and confirmed in game once (`confirmed`). It must not be worked out by the logic it tests.
  - **`expect.notStatus`** is for a shape whose rule is "nothing to learn" (a learned source, a look known from another item while the player has those hidden): a list of statuses that would be wrong. What such an item shows instead (`collected`, `sellable`, an upgrade, an auction price) is other rules' business, so no single status can be expected.
  - **A shape can only ask for a value,** so three facts are worked out for it: `levelMet` (the toon has the item's level); `lookKnownUsable` and `lookKnownUnusable` (another source of the look is collected, one this toon can use or one it cannot: the addon answers differently for the two); and `sameLookShown`, the setting the Plus statuses hang on. A setting is an input like the toon's level. A test that expects `ownPlus` asks for it switched on and has a twin for off that expects nothing to learn, so one of the two has cases whatever the player chose.
  - **A kind of toon is a class,** because a result is kept per kind and the last run is what a regression is told from. The retail tests share one pool, the items of the WoWUnit tests the addon shipped until 2026: each item's facts on the toon at hand say which shape it is a case of.
- **Snapshot** (`/cwtest snapshot base`, then `/cwtest snapshot` after a change): what the addon decides and draws for every item in the bags, and in the bank while it is open.
  - **Every session takes one by itself** and compares it with the last session's: the bags once the login record is written, the bank the first time it is opened, each against its own earlier record. The "before" of a change cannot be asked for by hand: the game is often closed while the code is changed, and the next login already runs the new code. A reload is a session too, so a comparison is between two loads of the code. The last twelve are kept (`test-results.lua snapshot`), since the reload that saves one has taken the next by the time it is read. Chat says something only when an item is drawn differently. None is taken at a stop of a rotation run, nor with `plan.autoSnapshot = false`. The two commands remain for a base that has to stay put over several sessions.
  - Each item goes through the addon's own queue and is drawn on a hidden 37 px button of the tests, under a stand-in for the Bags or Bank feature with a name of its own. So the result does not depend on the bag addon in use, and its requests share no queue key with the real windows.
  - Items are matched by link without the linking toon's level and specialization. Copies of an item are one case unless they differ. Only containers both snapshots read are compared; an item that came or went is listed, not judged. A change of the addon's settings is listed with the diff.
  - With **Enable debug** on, the stand-in's buttons show up in the export's `[Button Geometry]` as windows named `Tests:Bags` and `Tests:Bank`.
  - An item that was never drawn is listed with how far it got: whether the item load called back, whether its data is cached, and whether the addon's status is ready now.
- **Timing** (`/cwtest timing <label> [runs]`, `/cwtest timing idle [seconds]`; a login record is written by itself). The addon's time is the client profiler's "last frame" figure added up per frame, the share is computed as the addon list computes it (`GetAddonMetricPercent`), memory is `GetAddOnMemoryUsage`. A forced refresh is measured until the queue has been empty for 0.3 s. Whether the "last frame" figure means that is recorded by `profiler.metrics`, not known.
- **The core's counters** (section Counters; `Counters.lua` here). The tests wrap the core's functions as soon as they load, before their own hooks go on the same functions, so a hook's time is in no figure; the profile itself stays off.
  - **A timing needs no setting changed by hand.** Its measured runs go without the profile and without Enable debug, whatever either is set to, and both are put back afterwards (`T.MeasureUndisturbed`). The suspended setting is noted in the saved results, so a reload in the middle of a run puts it back at the next load.
  - A refresh timing ends with a counted pass: `plan.timing.countedRuns` more refreshes with the profile on and its figures started from zero, stored as `counted` and printed per refresh. They are not part of the record's medians, and their addon time beside the measured one shows what the counting adds. The pass resets the profile's figures.
  - The login record holds the ledger as it stood when the queue first went idle (`core`), an idle timing the refreshes by trigger during it, and every session adds its refreshes by trigger to the build's event totals. A refresh the tests forced is in there under the tests' own line. A login cannot be taken again without Enable debug, so its record only says when the setting was on (`debugOn`).
  - `/cwtest counters` prints the report and stores it (`test-results.lua counters`); `on` and `off` switch the profile, `reset` starts its figures from zero, and `login` profiles the next login or reload from the moment the tests load, with the result in that login's record.
- **Run it with the other addons on, as played.** They feed the verdicts (Pawn the upgrade arrow, Auctionator the auction icon, Questie the quest icon) and decide which buttons are drawn (a bag addon), so a run without them would guard and time something nobody plays. The set changes over time, so every session, snapshot and timing record names the set it was taken with: the addons enabled for the toon and their versions (enabled, not loaded, so one that loads on demand makes no new set), stored once under a key in `addonSets`. A snapshot diff lists what changed in the set since the base, and the timing listing says so between two records. A base set by hand is short-lived for the same reason: the older it is, the more of its diff is the other addons'. The comparison a session makes by itself is against the session before, and counts what differs in the set beside it. Timing figures taken with different sets are not a before and after.
- **Refused items.** The tests count every `GET_ITEM_INFO_RECEIVED` and `ITEM_DATA_LOAD_RESULT` that says an item could not be loaded, from their own load on. The login record carries the list. The events do not say who asked, so another addon's question is counted too; a refusal that arrives while a test is asking for items itself is counted apart.
- **Appearance sources** (`/cwtest sources`). The addon reads every source of an item's appearance, and a source can belong to an item this client cannot load. The probe takes every item the addon drew this session (kept by the counting hook on `ProcessItem`) and what the toon wears, lists their appearances' sources, and names each source item the client has no data for, with the drawn items that lead to it. An item the collection has no entry for can still have a look, which the addon finds by trying the item on a model; for those the probe asks the addon for the appearance instead of repeating that. For the first few it then makes the calls the addon makes on a source, one at a time (`GetSourceInfo`, `GetItemInfoInstant`, `GetItemSpecInfo`, `GetItemInfo`, `RequestLoadItemDataByID`), and records which of them the client answers with an event. Run it with the windows closed: a step during which the addon drew is marked as not clean. Ensembles are not followed.
- **Who asks for an item** (`plan.traceItems` in `Plan.local.lua`). A refused item that no drawn item's appearance leads to was asked for some other way, possibly by another addon. For the item IDs listed, every function of `C_Item` and `C_TooltipInfo` is hooked for the session and each call that names one is stored with its stack; the results listing prints the addons on it (`traces`). A call made while the addon draws an item is stored with that item. Nothing has to be typed in game. A caller that kept its own reference to a function from before the tests loaded is not seen, so a refusal with no call on record came that way or through another API. The hooks cannot be taken off, so the list is emptied again once the question is answered.
- **Pool search** (`/cwtest search [count]`). It walks the wardrobe's appearances, category by category in turn, and records items whose facts fit a verdict test's shape on this toon, one per appearance, with the addon's present status for each. It stops when every test has its items or at a limit of appearances, item loads or seconds. The result is a list to read: an item goes into `VerdictCases.lua` by hand, and the expected status stays the one written for the shape. A found item whose status differs from the expectation is the interesting kind: either the shape lacks a fact or the addon is wrong.
- **Bag states** (`Sightings.lua`, `/cwtest sightings`). Openable, locked, readable and refundable belong to one copy of an item in one slot, and a binding text depends on whether that copy is bound, so no pool of item IDs can stand for them. The bags are read after login and whenever they change (the bank while it is open), and a slot that fits a case is checked then: the client's facts about the slot against the addon's answer for it.
  - The facts come from the container, the purchase info and the slot's own tooltip (`C_TooltipInfo.GetBagItem`). The record also keeps what the tooltip of the bare link says, which is the one the addon reads: where the two differ, the addon cannot know the state of that copy.
  - The record keeps the type of the tooltip line that says "Locked" or "Right Click to Open" (`lockedLineType`, `openableLineType`): the addon reads a text only off the line types it lists.
  - Before the slot, the check asks for the verdict of the bare link, the way a mail or loot window does before the item reaches the bags (`linkStatus` in the record). The slot's answer must not be the link's.
  - A case is `pass`, `mismatch` or, for one without an expectation, `seen` (`accountBindType`: bind type 7, recorded with its tooltip lines). A case no item has shown is listed as not seen, per client.
  - The addon keeps one verdict per link, so two copies in different states share it. A record names the other copies' states (`otherCopies`), which tells that cause from a wrong rule.
  - Each item is asked about once a session, a limited number per case, and nothing is asked before the login record is written, during a timing, in combat or while another job runs. A mismatch is said in chat.
- **Integrations** (`Integrations.lua`, `/cwtest integrations`). The facts are the addon's own (section Integration Report); the tests add memory: one record per integration and version of the other addon, added to at the end of every session, with the items that integration drew. A hook point behind a window nobody opened is "not reached" in that session, so the record counts sessions. `ok` with draws is the proof that a hook delivers; after login a `problem` is said in chat.
- **Bag addon rotation** (`Rotation.lua`, its panel in `RotationPanel.lua`; `/cwtest rotation` opens the panel, `/cwtest rotation status`, `start [addon ...]`, `next`, `skip`, `check`, `abort` are the same typed). A bag addon replaces the bag window, so a session shows one of them, and the client switches addons only on a reload. A run visits Blizzard's own bags and each installed addon of `plan.rotation.addons` (`Plan.lua`; a new bag integration gets a line there), with that addon alone enabled for the toon and every other addon as it is.
  - **One reload per stop, each behind a typed command or a click** (`reload.timer`: the client refuses one without). The run is kept in the saved variables across its reloads, with what every addon it touched was before it. The set the toon plays with is the last stop, so a run ends where it began; `abort` puts the set back from any stop. The enabled set is per toon, so another toon is never changed.
  - **The panel is the way to run it.** Its one large button always names the next step and does it (start, open the bags, next stop, put the addons back, save the results), and it comes up by itself after every reload that is a step of a run, so nothing has to be remembered across reloads. "Open the bags" calls `ToggleAllBags`, the function behind the B key and the one bag addons hook (BetterBags hooks no other); it is only offered while no bag button is on screen.
  - What a stop's addon depends on is enabled with it and put back at the next stop. An addon that does not load is recorded as skipped, with the client's reason.
  - **The check knows nothing about the bag addon.** After a full refresh, every visible button the addon drew for a bag slot (kept by the counting hook on `ProcessItem`) is compared with that slot drawn on a hidden button under a stand-in for the same feature: icon, tint, text and level gain. Size and position are left out, they belong to the window. The button must also carry the new refresh generation, which fails a feature whose `Refresh()` does not re-run `UpdateButton`, and the picture on the button must be the picture of the item in the slot it was drawn for.
  - A stop passes only when buttons were checked, so bags left closed fail it. The stop's lines of the integration report are stored with it, and a `problem` there fails the stop.
  - Noted, not judged: a filled slot with no visible button (a collapsed group, a merged stack), a button dimmed by a search, a button that names another slot than it was drawn for, a visible bag button drawn by a feature that is not the stop's.
  - **Before and after a change to an integration:** what each button showed is kept per item, here with size and position, and a finished run lists what differs from the run before it on that toon.
  - "Check now" (`/cwtest rotation check`) makes the same check on the bags as they are, without a run. `luajit tools/test-results.lua rotation` prints the runs.
  - **Which of the listed addons a client can load:** on Forever ArkInventory 31217, Baganator 860, Bagnon and Bagnonium 12.1.11, BaudBag 12.1.5.1, BetterBags 0.9.3 and Inventorian 12.1.5.1 loaded and were visited (2026-11-15); ElvUI names `16001` in its TOC and was not installed. LiteBag, KkthnxUI and NDui have retail and classic TOCs only. A stop whose addon the client will not load is recorded as skipped.
  - **When a stop draws nothing, its record says where it stops:** how many draws each of the stop's features asked for in the session (`UpdateButton`, and how many of those for an empty slot) beside how many were made. No requests means the other addon never called the hook; requests for empty slots only, that the bag and slot handed over are wrong.
  - **Two buttons of one feature for one slot** (BetterBags' food and drink bar beside its bag): the check names a button that was not drawn again and shares its slot with another, hidden or not. That is how the queue's one request per location was found (section Processing Pipeline).
  - **The picture check cannot be made on BetterBags:** it draws the item's picture on a frame of its own, and the button the addon decorates has an empty `icon`. The record says so.
  - **Evidence.** Offline: a mocked client with planted faults (a `Refresh()` that does nothing, a stale icon, another item's picture, an addon that does not load, two buttons for one slot). Forever client (1.60.1.70938, hunter, 49 filled bag slots, eight stops by the panel's buttons): the addons were switched as announced and put back at the end; Blizzard's bags, Baganator, Bagnon and Bagnonium passed with all 49 buttons showing what the hidden button shows, drawn again, and carrying their item's picture. BaudBag and Inventorian showed the right content and were not drawn again while their `Refresh()` was empty, and passed in a second run once it was not. ArkInventory showed no items of its own accord, so its integration is unseen. Between the two runs nothing was shown differently at any stop. Retail not seen.
- **Journal:** every learn event (appearance source, recipe, toy, mount, pet, level) with what happened in the six seconds before and the second and a half after: bag contents gained and lost, equipment changes, quest turn-ins, vendor / bank / mail open. `likely` is a guess from those ("sold to a vendor"). The same file counts `RefreshItems` and the events suspected of triggering it needlessly, per minute of play.
- **Waiting without `pcall`:** tests run as jobs in a coroutine, one at a time. The client's Lua cannot yield across `pcall`, `xpcall` or a secure hook, so `T.Protected` runs a test in a coroutine of its own instead; a `pcall` may only wrap a call that does not wait.
- **Where the tests know the core's insides:** `T.CoreIsIdle` (the queue's fields), `ReadDrawn` in `Snapshot.lua` (the overlay's `mogStatus`, `bindsOnText`, `upgradeDeltaText`, `caerdonHasUpgradeBadge`), the counting hooks on `RefreshItems` and `ProcessItem`, `CaerdonEquipment.failedSourceItemLoads` (the sources probe), an item's `customDataLoaded` (a never-drawn snapshot entry), `CaerdonIntegrations:GetReport()` (the integration records), `CaerdonCounters` (`Attach`, `Force`, `Reset`, `GetReport` and the shape of the report) and the refresh generation, `GetRefreshGeneration` and `GetButtonRefreshGeneration` (the rotation's "drawn again" check, which also reads the button and the location off the `ProcessItem` hook), and for the recorder the six cache invalidations `RefreshItems` makes and the try-on model `CaerdonWardrobe.dressUp`. - **Packaging:** the packager (BigWigsMods, `parse_ignore`) turns an `ignore` entry that is a folder into `<folder>/*`, and skips untracked files by itself. Read in its source; not yet checked in a released zip.
- **Recorder** (`Recorder.lua`, `/cwtest record`): the client's answers behind one verdict, for the offline harness. Section Offline Harness.
- **The stopwatch is `GetTimePreciseSec`**, not `debugprofilestop`, which any addon can restart with `debugprofilestart`.
- **A measurement starts on a fresh frame.** The client's timers and the elapsed time an `OnUpdate` gets both count whole frames, and reading the addon's memory (`UpdateAddOnMemoryUsage`) makes one long frame (about 0.13 s on a retail toon with a large heap). Measured in that same frame, the time went missing: the first draw seemed to come 62 to 107 ms after `RefreshItems`, before the refresh's 0.1 s delay could be over. - **Memory per refresh is exact and repeatable** (the same figure to a tenth of a KB run after run), and a run in which the client collected garbage shows a large negative figure and is left out of the median.
- **A file added to the TOC is found by a plain `/reload`** (Forever client, 1.60.1.70938); no restart of the game is needed.
- **In game (2026-11-15, Forever 1.60.1.70938 and retail 12.1.5.70783):** the addon loads, the contracts run by themselves after login, the Save button's reload is recorded, and a snapshot base, forced refresh timings at the bank, bags and vendor and an idle timing were recorded in each client. ## Offline Harness

`tools/harness/` runs the addon's real Lua under LuaJIT in a mocked client. `luajit tools/harness/run.lua` runs everything and exits 1 when something failed (2 for a problem with the setup); its head lists the commands and options. It needs the source and listings mirrors. It is offline evidence: it shows what the addon's code decides from a given set of answers, never what a client answers.

- **What is real and what is mocked.** Real: the addon's item side (every file the TOC loads outside `features/`, `external/`, `config/`, `libs/` and `localization/`), and Blizzard's own Lua that it runs on (`Mixin`, `Item`, `ItemLocation`, `ContinuableContainer`, `LinkUtil`, `Color`: the list is `tools/harness/blizzard-base.lua`, loaded from the source mirror of the flavor). Mocked: the client itself (`client.lua`): Lua's helpers under their global names, the clock, frames, events, timers, secure hooks, the error handler. Everything the game knows comes from a provider: a recording, or a hand-made game.
- **Each mocked client is a world of its own.** What is loaded into it sees the client's table as its globals (`setfenv`), so two clients in one process share nothing.
- **Two guards make LuaJIT as strict as the client's Lua 5.1** (`lua51.lua`): no yield inside `pcall`, `xpcall` or a secure hook, and `%s` only for strings and numbers. They hold for the whole process, the harness included.
- **A frame** is a table with a userdata at `[0]`, as in the client. A method the listings name for any widget exists on it and does nothing; a handful that logic depends on are implemented (events, scripts, shown, parent, name, text, size). A field nobody set reads as nil, so `if button.overlay then` works.

### Recording (`/cwtest record`, `CaerdonWardrobe_Tests/Recorder.lua`)

- **What a recording is:** every answer the client gave while the addon decided about one item, with the verdict it reached. `/cwtest record <item ID or link> ...`, `slot <bag> <slot>` for a copy in the bags, `bags` for one of each item carried; `list` and `clear`; `plan.recordItems` for IDs to record after login. Then `/reload`, and `luajit tools/harness/run.lua import`.
- **How the answers are caught.** Every client function the addon names gets a secure hook. A hook is told what a function was asked, not what it answered, so the recorder asks the same question again at once and keeps that answer. That is only done for a function whose name says it reads (`Get`, `Is`, `Has`, `Can`, `Unit`, ...; `RecordKeys.lua` holds the rule and the exceptions). A function that does something (`Request...`, `Set...`) is not hooked.
- **The client refuses a secure hook on some functions** ("hooksecurefunc(): GetCurrentEnvironment is forbidden for hooking", Forever client 1.60.1.70938, 2026-11-16). Which others it refuses is not listed anywhere, so the recorder tries each one protected, passes over a refusal, and lists the function with the client's words in the environment (`notHooked`) and as a count in its chat line. A recording has no answers for such a function. The mocked client refuses the same name, and a scenario plants a second one.
- **A function that hands its answer to a function it is given** (Auctionator's `DBKeyFromLink`, which the addon uses to reach the listing history) is asked again with a function of the recorder's own, and what that was called with is kept (`callback` in the answer); a replay calls the addon's function with it. Such functions are listed by name (`CALLBACKS` in `RecordKeys.lua`) and must call back at once.
- **The hooks stay until the next reload.** A secure hook cannot be taken off. They do nothing while no recording runs, but every call of a hooked function then costs one more call, by anyone. Reload before a timing.
- **The names come from the static check.** `--emit-facts` writes `CaerdonWardrobe_Tests/ApiNames.lua` (generated, not tracked): every global the addon reads and every field it reads off one, every literal hook target, every string literal that is a global string, and what Blizzard's base files (above) ask the client, since `Item.lua` calls `C_Item` functions the addon never names. A name the addon builds at run time is not in the code and goes into `ALSO_NAMES` in `RecordKeys.lua`.
- **A recorded run is one call from start to end.** The item is asked for twice: once to get everything loaded, then, recorded, with the addon's caches emptied first (the same ones `RefreshItems` empties) so it asks the client for everything again. Because nothing waits, no other addon's calls are in it. If the addon does have to wait after its caches were emptied, the last tries leave the caches alone and the recording says so (`cachesKept`).
- **At the end of every run the recorder asks about the toon itself** (level, class, race, faction, professions, what it wears), whether the addon asked or not, so the addon's setup at load finds those answers in a replay.
- **Once a session, the environment:** what every name of that list is in this client (a string or number with its value, a table, a function, a frame, or absent), and the saved variables `CaerdonProfessionData`, `CaerdonRecipeData`, `CaerdonAuctionData`. The settings are copied into each recording.
- **Another addon's table that the addon walks through itself** (`PawnCommon.Scales`) is kept as an outline in the environment (`tables`): its keys, and the plain values one level down, which is what the addon reads off a scale. Only a table the addon names by a path below another addon's global, and only up to a size.
- **Seams: where a recording takes the addon's own answer.** The quest module builds an index over every quest in QuestieDB, over several frames, once a session, and reads Questie's own module tables; neither fits into a recording of one call. So what that data says about one item is asked through two methods of the module, `GetIndexedQuests(itemID)` and `GetQuestieHiddenReason(questID)`. The recorder keeps what they answered, and a replay puts that in their place (`SEAMS` in `RecordKeys.lua`): the code that judges a quest runs for real on recorded facts (each `LibQuestieDB.Quest.Get` it makes is an ordinary recorded answer), the code that gathers them does not run. A seam the recording has nothing for is left as the addon defines it. A new seam is a method that returns plain data for one item, and a line in that list.
- **What the addon asks once a session** (`ONCE_A_SESSION` in `RecordKeys.lua`: QuestieDB's contract check, with the version the addon asks for) is asked again by the recorder at the end of every run, since a replay starts a session of its own. When the addon changes what it asks, a replay names the new question.
- **A module that keeps something for the whole session gives the recorder a way to forget it.** `RefreshItems` rightly leaves alone what never changes: the food and drink module keeps each item's classification (what it restores, at which level) and judges a food against every other food carried. In a session that had seen those foods the recorded run asked the client nothing about them, and a replay, which starts with nothing, asked and had no answer (Forever client: every food in the bags was rejected at import, each with the other foods as its unanswered questions). So the module has `ForgetClassifications()`, which nothing in play calls and the recorder calls with the other cache invalidations. A module that turns up the same way in an import gets the same.
- **What it cannot catch:** a method called on a frame or on another addon's object (Questie's modules, Auctionator's callback API), a table of another addon read deeper than the outline above, and state the addon built before the recording from calls it does not repeat. The one frame method that is recorded is the try-on model's `GetItemTransmogInfo`. The import says when one of these mattered.

### Fixtures (`tools/harness/fixtures/<flavor>/`)

- **A fixture is two files:** the recording of one item (`<class><level>-<item ID>-<name>.lua`) and the environment of its session (`env-...lua`, one for all recordings of a session). Plain Lua tables with sorted keys.
- **An answer that two recordings of a session agree on is kept once,** in the environment's file (`calls`): the quest log, what the toon wears and who it is are asked for every item. A replay looks in the recording first. An environment file that is already there only grows, since fixtures written earlier rely on it.
- **The tooltip's `dataInstanceID` is set to 0 on import.** The client numbers every tooltip it hands out, so no two answers would compare equal; the addon does not read the number.
- **A question is stored under its arguments as text** (`RecordKeys.Args`), which the recorder and the harness compute with the same code: the harness loads `RecordKeys.lua` itself. Trailing nils are dropped; a table argument is its data, without its methods.
- **The import replays before it writes.** A recording whose replay does not reach the recorded verdict, that left a question unanswered, or that made the code read a name the environment does not have, is rejected and not kept. What it lists is what the recorder missed.
- **Names are replaced on the way in,** since the repository is public: the toon, the realm, and every other toon the saved data names become `Toon1`, `Realm`, `Toon2`, ... The client names a realm in more than one way (`UnitName` returns another form beside the name than `GetRealmName` does), so every form a recording holds is collected, and a file in which one is still found is not written. A recording in which a call was made with one of those names cannot be converted (the arguments are text with lengths) and is refused. The fixtures still show what the toon carries, wears and has in its quest log.
- **A second recording of an item does not overwrite the first** (`--replace` does). A fixture keeps the state it was taken in: learning the item later does not change it.
- **A replay ends as** `pass`; `differs` (every question had its answer and the verdict is another: the code decides differently than it did); `stale` (the verdict is another and the code asked something the recording does not hold, so it cannot judge this code: record again); or `error`. A pass with unanswered questions says how many.
- **What a replay does not have:** the addon's setup at load asks the client things no recording holds (it happened long before); those are counted apart and do not fail a replay. Settings are the recorded ones as they were, with no migration run on them. A global string or enum value the recording lacks is taken from the listings mirror and counted, since it is the mirror's build and not the recording's.

### Scenarios

- **`scenarios/recorder.lua` is the round trip:** the real recorder records a hand-made game (`game.lua`), what it saved goes through the saved variables text and the import, and the replay has to reproduce it. Then the faults a replay exists to find are planted one at a time. The game's answers were written by hand from what the code asks, so this proves the machinery and nothing about the game.
- **`scenarios/equipment.lua` is the item code on one hand-made item per case:** the item's getters, the fields of `GetTransmogInfo()` (needed by this toon, by another, learned, known from another item, above the toon's level) and the status that comes of each, with the "same look" setting off and on. It also asks the housing gate that decides whether an item's data is still on its way; `CaerdonHousingMixin.DebugIsHousingDataPending` exists for that.
- **`scenarios/verdicts.lua` is the test addon judging:** its real runner, facts, verdict tests and the canary contract against the hand-made game, with tests of the scenario's own beside them (a wrong expectation, a setting switched on, a build that changes an item).
- **`standalone/`** holds the tests that are older than the shared client, each with a small client of its own, run in a process of its own: the core's counters, the bag addon rotation, the `Refresh()` of two integrations against stubs.
- **A new scenario** is a file in `scenarios/` that returns `function(H, S)`; `S.Check` and `S.Equal` count.

## Counters

`CaerdonCounters.lua` is the first file in the TOC, so its clock starts with the addon's first line. It has two parts, and the export prints both under `[Counters]`.

- **The ledger is always on,** because login is where it matters. It is written only where the thing happens:
  - *Milestones* (seconds since the first line): `addonLoaded`, `playerLogin`, `enteringWorld`, `bagUpdate` (the first `BAG_UPDATE_DELAYED`), `firstRequest`, `firstDraw`, `queueIdle` (the queue first empty after a draw).
  - *Loads asked of the client,* counted in the listener (`CaerdonAsyncCallbackSystem.lua`), so every path is in it and no caller has to remember: asked, loaded, failed, not answered, with who asked. A failure keeps the item, the line that asked, when, how long the answer took, and whether the toon was in the world and the bags had reported. Requests made through Blizzard's own `Item:ContinueOnItemLoad` do not pass the listener and are not counted.
  - *Who asked* is the feature's name for a request the queue makes, otherwise the outermost file of the addon on the stack (`features/Merchant.lua`). What a callback asks for next (the source items of an appearance) is filed under whoever asked for the first, since that stack holds only the listener.
  - *Full refreshes by trigger:* the event the core's frame was handling, otherwise the line that called `RefreshItems` (`CaerdonQuestItems.lua:134`, a timer of the core by its own line). A line label moves when the file is edited, so compare counts within one version.
- **The profile has a switch of its own** (`Counters:SetProfile`) and costs nothing until it is first used: the functions are only wrapped then. Wrapped and off, a call costs one extra function call.
- **It does not follow Enable debug.** That setting makes every draw do more (it records each button's geometry and adds tooltip lines), so a profile taken with it describes an addon nobody plays. Nothing in the addon switches the profile on; the test addon does.
  - *Per function:* calls, time, worst call, memory, each also as "own": without what it spent in the other wrapped functions it called. `GetCaerdonStatus` is counted per outcome (computed, cache hit, tooltip not ready, no link); the three `Counters:Mark` lines in it say which.
  - *Wait in the queue:* from the first request for a button that is not yet drawn to its draw.
  - *Drains:* one run of the queue's coroutine. Time and memory are taken around each pass, so they are the whole pass, hooks of other addons on the core's functions included, and nothing of the frames in between.
- **Items and item data copy their methods when they are created,** so a wrapper only reaches those created after it. The test addon wraps as it loads, which is before anything is drawn. Functions on the frame and on the features are reached at once.
- **Memory is `collectgarbage("count")` around the call,** which is every addon's memory, not this one's: it is right as long as nothing else runs inside the call. A sample in which the collector ran is negative, is left out and is counted (`collected`), and one in which it only swept reads low. The test addon's memory per refresh (`GetAddOnMemoryUsage`) is the exact figure; this one says where it goes.
- **The time of a wrapped call includes the clock reads of the wrapped calls inside it** (two per call), so with the profile on a refresh costs more than without. The test addon measures without and counts in separate runs.
- **A new function to time** is one `Probe` line in `Counters:Attach`. One that a wrapper cannot see into gets a `Mark`, or an `if CaerdonCounters.on` line where it happens; keep those to places the wrapper cannot reach.
- **Evidence.** Offline: the real module, listener, feature mixin and queue against a mocked client whose clock and memory figure are the mock's own, so every expected figure is exact (calls, own time, memory, the outcomes, a collector run, an error inside a wrapped call, a function that is gone); the item and status code and the drawing were mocked. Forever client (1.60.1.70938, a rogue with BetterBags): callers and triggers are named as above, every function is counted, computed plus cache hit equals the draws, the drains account for 80 to 88 % of the memory the client reports per refresh (the rest is allocated outside the passes), and the profile adds about 2 % to a refresh's addon time. Retail not seen.

## Transmog on Forever

Selling an item to a vendor teaches its appearance ("added to your appearance collection"), with no equip or bind. The collect APIs do not model this, so three flags on `GetTransmogInfo()` cover it. All need both collect verdicts (`PlayerCanCollectSource`, `AccountCanCollectSource`) to be ready.

- **`validSourceNotCollectable`** (and `...KnownLook`): `isValidSourceForPlayer` true, no `useErrorType`, both collect verdicts false. Becomes `own` / `ownPlus`. Red tooltip text is not required: cloth on a hunter (Spellbinder Vest 2969) has this shape with a white tooltip, as does mail under level 40 (Soldier's Wristguards 6550) with a red one. It is `own`, not `lowSkill`, because selling teaches it at once (confirmed in game).
- **`proficiencySourceNotCollectable`** (and `...KnownLook`): `isValidSourceForPlayer` false, `useErrorType` 10, both collect verdicts false (Blazing Wand 5212 on a hunter). Becomes `other` / `otherPlus`: `own` is strictly for appearances the toon can transmog into (author decision). Retail answers "can collect" for such sources, so the flag does not fire there. Errors 7 / 8 / 9 are not covered. Not confirmed in game.
- **`noCollectionCategory`:** both flags are skipped when the item's own `sourceInfo.categoryID` is `Enum.TransmogCollectionType.None`. Arclight Spanner 6219: `C_TransmogCollection.GetItemInfo` is nil, the dress-up fallback still yields a source, and `CanItemTransmogAppearance` is false. Such a source teaches nothing (inferred, not tried in game). `needsItem` / `otherNeedsItem` still follow the collect APIs.
- **A look can list a source whose item this client cannot load.** Appearance 63650 of Arclight Spanner 6219 has a source that belongs to item 216679, which `DoesItemExistByID` accepts and the server refuses. Asked about such a source, `C_TransmogCollection.GetSourceInfo` (it returns a table without `name`), `C_Item.GetItemSpecInfo` and `C_Item.GetItemInfo` each make the client ask the server, and each question is answered about 0.3 s later with `GET_ITEM_INFO_RECEIVED` and `false`; `RequestLoadItemDataByID` with a failed `ITEM_DATA_LOAD_RESULT`. `C_Item.GetItemInfoInstant` answers at once and asks nothing. The client does not remember the refusal: the same question draws the same event again. Other addons redraw on that event, so a question repeated on every refresh costs more than the call (seen in game with `/cwtest sources`).
- **`PlayerCanCollectSource` is true on Forever for a shirt:** Brawler's Harness 6125 on a hunter answers true for the toon and for the account, with a valid source and no use error, and the addon shows `own` through the ordinary path (probe, Forever client 1.60.1.70938). It was false for every other uncollected piece seen from that hunter (armor of every type, weapons). Whether a shirt is the only kind is not known.
- **Unconfirmed, on Forever and on retail:** completing a quest seems to teach the look of every reward choice, whichever one is taken; a class-specific exception may exist (author observation, no export). If it holds, a learnable icon on a choice is no reason to pick it, and the order for choices would be upgrade, then sell value.
- **Red tooltip text is authoritative for equippability.** `CaerdonItem` scans every tooltip line, both columns, for `RED_FONT_COLOR`. Armor proficiency red sits in the right column of the `EquipSlot` line. `bindingResult.unusableItem` forces `canEquipForPlayer = false` and drops `isUpgrade` unless the shortfall is level-based (`upgradeLowSkill`).

## Ensembles

Ensembles teach **sources**, not appearances. Check `sourceInfo.isCollected`; do not skip a source because the appearance is known from another one (difficulty variants are separate sources and count toward set completion).

- **`own`:** uncollected sources wearable by this toon. **`ownPlus`:** an ensemble for another class with wearable extras (cloak, cosmetics). **`other`:** nothing wearable, but learnable for the collection. **`otherNoLoot`:** every remaining source needs another class, race or faction.
- **`sourceInfo.useErrorType` is the only reliable discriminator:** 7 Class, 8 Race, 9 Faction are true restrictions; 10 ItemProficiency (armor type) is not. `PlayerCanCollectSource`, `AccountCanCollectSource`, `meetsTransmogPlayerCondition` and `isAnySourceValidForPlayer` answer the same for both kinds once the account has a toon of the required class.
- **Mixed:** `other` if any remaining source is only armor-type restricted; `otherNoLoot` only when all are truly restricted.
- **Vendor gray-out:** never fade `own`, `ownPlus`, `other`, `otherPlus`, `lowSkill`, `lowSkillPlus`, `otherNoLoot`.
- **Open question:** ensemble 241380 taught a Monk-only source (78758, `useErrorType` 7) to a Druid, so error 7 may only block equipping and `otherNoLoot` may be too strict. Test: ensemble 139167 (Paladin-only item 144275) on a level 45+ non-Paladin plate wearer.

## Upgrades

`CaerdonEquipmentMixin:GetTransmogInfo()` carries the upgrade verdict and its inputs.

- **`isUpgrade`:** Pawn's verdict, else the unique-upgrade heuristic, else `upgradeItemLevelDelta > 0` (unless unique-blocked). `pawnIdentifiedUpgrade` is true only for Pawn's own verdict (yellow arrow; green means item level).
- **`equalItemLevelEquipped`:** same item level as equipped and equippable. Such a collected item is not `sellable`; it shows the neutral balance icon (`Icon.SameLevelBehavior`) unless it is off-spec, a tabard / shirt, or in a gear set.
- **`identicalToEquipped`:** the exception to the line above. A tie is only worth keeping when the piece does something the equipped one does not, so a piece that matches every equipped piece it ties is a duplicate: no protection and no balance icon under any `SameLevelBehavior`, and it counts as redundant (its use or equip effect is one the toon already has). Two checks, both must pass (`IsIdenticalToTiedEquipped`):
  - `C_Item.GetItemStats` tables equal. The table has no weapon speed or damage range, no effects and no set bonus, so it cannot decide alone; when either item has no table the lines decide.
  - `C_TooltipInfo.GetHyperlink` lines equal as text, in order. Ignored: name, binding, sell price, item level, flavor text, usage requirements, blank lines and the durability line. Everything else counts, including the slot line's armor / weapon type and any line type not listed, so a doubt reads as "different".
  - An enchant on the equipped piece alone is skipped; one on the candidate counts. With two slots, a tie against a different piece in the other slot keeps the protection. Empty line lists (data not loaded) never match.
  - A different item level with the same stats needs no rule here: the upgrade verdict or `betterItemEquipped` already decides it.
  - **Export:** `identicalToEquipped` and `equippedLineComparison` (per slot: what matched, or the first difference). Confirmed in game for two plain cloaks with the same armor; the rest is offline, and what `GetItemStats` returns on Forever (armor, enchants) has not been recorded.
- **`canEquipForPlayer`:** Blizzard's collect logic plus the tooltip scan. **`upgradeMatchesSpec`:** off-spec upgrades keep the arrow, tinted red, when "mismatched spec" is on.
- **Gear set items** suppress the arrow; only the level gain text remains. **Tabards** never show as upgrades.
- **Legendaries** with a use or equip effect are never `sellable`.
- **Pawn vs. item level:** `betterItemEquipped` only overrides a Pawn upgrade when PVP scaling took part (`HasBetterOrEqualEquippedItem`'s second value). Otherwise Pawn's stat weights win.
- **`pawnPrefersEquipped`** blocks the item-level fallback when Pawn scores the equipped piece at least as high on every visible scale. `PawnShouldItemLinkHaveUpgradeArrowUnbudgeted` returns false for both "not better" and "cannot judge", so `PawnPrefersEquipped` compares scores itself (`PawnGetSingleValueFromItem`, the weaker of two slots, 0.5% threshold) and gives no verdict for trinkets, an empty slot, missing data or no visible scale. Equal at zero on every scale counts as "not better" (author decision; the cost is that gear a class's scales ignore never gets an item-level arrow). Only applies while `PawnCommon.ShowItemLevelUpgrades` is off (Pawn's default on classic-era clients, on by default on retail).
- **`pawnOffTreeUpgrade`:** without specializations Pawn shows one scale per talent tree and answers "an upgrade for any visible scale". When every scale the upgrade is for belongs to a tree other than `GetPrimaryTalentTree()`, the arrow stays but is drawn in the off-spec red (author decision), independent of `Icon.ShowMismatchedSpecUpgrades`. Pawn's scale list is the setting: hide a scale in Pawn and its arrows go. Nothing is ignored when no tree leads, the own tree's scale is hidden, or one scale is visible; custom scales count as the toon's own. Pawn's druid numbering is 1 Balance, 2 Feral (Damage), 3 Feral (Tank), 4 Restoration. Confirmed in game for a Beast Mastery hunter; the rest is offline.
- **Armor class guard:** the item-level fallback never fires for a lower armor class than the piece equipped (`IsLowerArmorClassThanEquipped`). Pawn may still flag it.
- **Upgrade badge:** an upgrade whose status became something else (a look to learn) keeps `bindingResult.upgradeStatus` (`"upgrade"` / `"upgradeLowSkill"`), taken after the red-text correction. `SetItemButtonStatus` then draws a small ring and arrow on the icon's corner (`UPGRADE_BADGE_SCALE` 65% of the icon, moved `UPGRADE_BADGE_OVERLAP` 40% in), at the corner taken from `icon:GetPoint(1)`. It follows the upgrade arrow's settings, has none of its own, and shows and hides with the icon through its `OnShow` / `OnHide` hooks. Where a window does not show the status' own icon, the item draws as a plain upgrade. Confirmed in game, including Baganator and auction rows.
- **Export:** `pawnComparison`, `pawnUpgradeScales`, `pawnScaleFilter`, `pawnOffTreeUpgrade` under `[Transmog (Caerdon Processed)]`; `Talent Trees` under `[Player]`.

## Sellable Rules

Equipment is `sellable` when it is `collected`, redundant or without use / equip effect / set, and not protected. Never sellable:

- **Fishing poles** (weapon subclass `Fishingpole`).
- **Profession tools:** a Weapon with a met skill requirement line (`bindingResult.skillRequirementMet`; armor with a profession requirement is judged normally), or anything `GetProfessionToolInfo()` names.
- **Equal item level** unless the piece is `identicalToEquipped` (see Upgrades), recraftable items, legendaries and cosmetics with an effect, tabards with a use, teleport items, artifacts.

Other sources of `sellable`:

- **Equippable junk** (`IsEquippableJunk`): Miscellaneous / Junk that goes in an equipment slot with no use, no equip effect, no appearance, and a vendor price. Built for the trophy fish (15 Pound Mud Snapper 6295). Keep it this narrow.
- **Consumables for another class** (`IsOtherClassConsumable`): a red `UsageRequirement` line of type `RaceClass` (`bindingResult.raceClassRestricted`). Needs a vendor price; account-bound and warbound-until-equip are skipped. Built for mage scrolls on a hunter. Not confirmed in game.
- Recipes, food and drink, bags: their own sections.

## Profession Tools

`CaerdonProfessionTools.lua` says which items are tools of a profession the toon has; `GetProfessionToolInfo()` returns nil or `{ isTool, professions, toolName, source, match }`. A tool is never `sellable` or `auctionGoods`; nothing else changes.

- **Known items** (`KNOWN_TOOLS`): Mining Pick, Skinning Knife, Blacksmith Hammer, Arclight Spanner, Gyromatic Micro-Adjustor. Gathering has no recipe that names its tool. Gated on `C_PaperDollInfo.IsRangedSlotShown()` as a stand-in for "tools are carried in the bags".
- **Recipe tools:** `RecordRecipeTools` in `types/RecipeMixin.lua` saves every `Enum.RecipeRequirementType.Totem` name from `C_TradeSkillUI.GetRecipeRequirements` into `CaerdonRecipeData[realm][toon].tools[professionName] = { skillLine, names }`, for the toon's own profession only. A dropped profession's entry stays and is ignored.
- **Matching:** a known item, a name equal to a tool name, or, for equippable items, a name containing a tool name of 8+ characters ("Keen Skinning Knife"). The last is a guess.
- **Refresh:** new tool names and a changed set of professions (`SKILL_LINES_CHANGED`) call `RefreshItems`.
- **Not covered:** stand-ins under an unrelated name (Finkle's Skinner). Unverified: that `GetRecipeRequirements` names tools by the item's name, and that Forever-only hammers and knives work as tools.
- **Export:** `[Profession Tools]`. **In game:** the author's miner / engineer no longer sees the coin on his tools; a Skinning Knife on a toon without Skinning correctly does.

## Bags for the Bag Slots

`CaerdonBagSlots.lua` holds a bag item against every bag slot it fits; `GetBagSlotInfo()` is nil for anything that is not a bag or quiver (fields are documented above `GetItemInfo`).

- **Verdicts:** `isUpgrade` (a slot it fits is empty, or it beats the bag in one) becomes `own`, or `lowSkill` with red tooltip text. `isSpare` (every slot it fits is filled and it beats none) becomes `sellable` when it has a vendor price. Neither when a comparison cannot be decided.
- **Slots are read, not assumed.** `ReadSlot` classifies the item that is really there.
- **Kinds and the slots they fit** (confirmed in game on Forever unless noted):
  - `bag` (Container / Bag): normal slots, containers 1 to `NUM_BAG_SLOTS`.
  - `reagent` (Container / Reagent): the reagent slot, container 5. Assumed not to fit a normal slot.
  - `profession` (any other Container subclass): normal slots and, on Forever, the reagent slot. Retail's reagent slot is believed not to take them, so it only counts where `IsRangedSlotShown()` is true or once one has been seen in it.
  - `quiver` (item class Quiver; quiver and ammo pouch): normal slots only.
- **Better than the bag in a slot (`Compare`):**
  - Same kind and subclass: more slots. Equal is a spare.
  - Ordinary bag vs. profession or reagent bag: at least as many slots, since it holds anything.
  - Reagent bag vs. profession bag: more slots.
  - Undecidable, so no verdict either way: reagent bag vs. a profession bag with as much room or more; profession bag vs. a reagent bag, another profession's bag, or a smaller ordinary bag. What a reagent bag holds compared with a profession bag is unknown.
  - Quivers are only compared with their own subclass; against any bag the pair is skipped.
- **An empty slot only counts when the toon has a use for the bag (`hasUse`):** a quiver needs a bow or crossbow equipped, an ammo pouch a gun (`ReadAmmoWeapons`); a profession bag needs a profession in `PROFESSION_BAG_USERS` (the one its subclass is named after plus the crafting professions that use the same materials; a soul bag needs a warlock). One of the same kind already equipped also counts.
- **Size of an unequipped bag:** no API; the tooltip's "6 Slot Bag" line is read through the `CONTAINER_SLOTS` format.
- **Refresh:** `BAG_UPDATE_DELAYED`, `BAG_CONTAINER_UPDATE` and `SKILL_LINES_CHANGED` compare a signature of the slots and professions.
- **Settings:** `Icon.ShowBagUpgrades`, `Icon.ShowSpareBags`. **Export:** `[Bag Slots]`, printed for every item.
- **In game:** seen working on Forever (2026-11-14). Not individually confirmed: quivers, the retail gate, a profession bag on a toon without the profession.

## Recipes This Toon Has No Use For

`GetUnneededRecipeStatus()` replaces `collected` on a Recipe the toon knows or cannot learn.

- **`other` / `otherPlus`:** the recipe can be handed over (not soulbound, not bind on pickup) and another toon on the realm has the profession without the recipe in its recorded list. Plus when some toon already knows it. No vendor price needed.
- **`sellable`:** this toon knows it and nobody else wants it. Needs a vendor price; never for account-bound or warbound-until-equip.
- **Left on `collected`:** a known recipe when another toon has the profession but its recipes were never recorded.
- **"Known" for `sellable`** is `bindingResult.alreadyKnown` (the client's tooltip line) only. The name-based `recipeInfo.learned` cannot tell recipe ranks that share a name apart.
- **Data:** `GetRecipeOtherToonInfo()` wraps `CaerdonRecipe:GetOtherToonRecipeInfo(item)`, which returns `{ professionName, recipeName, knownByPlayer, toons, missing, unknown }`. Saved variables: `CaerdonProfessionData[realm][toon]` (ranks) and `CaerdonRecipeData[realm][toon]` with `knownRecipes` and `scannedProfessions`.
- **Recording (`GatherRecipes`):** only the toon's own profession (not linked, guild or NPC). `scannedProfessions[name]` is set only when the list is complete: `GetAllRecipeIDs` exists, or the `GetFilteredRecipeIDs` fallback ran with default filters and no search. Older data has no `scannedProfessions`, so other toons start as `unknown` until they open each profession once.
- **Tooltip (`TooltipMixin:AddRecipeLearners`):** green "Could be learned by: ..." for `missing` toons; gray "Recipes not recorded yet ..." only when the tooltip says "Already known". Wrapped in `xpcall`, because an error would leave `tooltip.caerdonProcessing` set.
- **Settings:** `Icon.ShowRecipesForOtherToons`, `Tooltip.ShowRecipeLearners` (a missing `Tooltip` section reads as on). The icon goes through `otherIcon`, so the per-window toggles apply.
- **Not modelled:** faction, the other toon's rank, other realms, deleted toons.
- **In game:** not seen. Export: `[Recipe]`.

## Outgrown Food and Drink

`CaerdonFoodDrink.lua` marks food or drink `sellable` when the toon carries a better one of the same kind it can use now; `GetFoodDrinkInfo()` is nil for anything else.

- **Compared with what is carried (bags only),** so the last stack is never marked.
- **Candidates:** Consumable / Food & Drink (subclass 5). The gate matters: a healing potion would otherwise read as food.
- **Food vs. drink:** no API; the tooltip line with a number and the localized `HEALTH` / `MANA` word decides (`both` is left alone). The first number is the amount. More numbers than "amount, duration" means buff food, which only competes with other buff food. The trailing cooldown note and `|4` plural escapes are stripped before counting.
- **Better:** higher required level, or the same level and a larger amount.
- **Never marked:** crafting reagents, items not usable yet, anything with quest value.
- **Hunters:** food must also be more than 20 item levels below the toon (`HUNTER_FOOD_LEVEL_GAP`), since a pet eats low food. Unverified on Forever.
- **Setting:** `Icon.ShowOutdatedFood`. **Export:** `[Food and Drink]`. **In game:** one buff food classified correctly; an "outdated" verdict is offline only.

## Quest Value

`CaerdonQuestItems.lua` gives the `quest` status to items of any class that an unfinished quest takes; `GetQuestItemInfo()` returns nil or `{ hasQuestValue, isActive, isUpcoming, quests }`.

- **No client API maps an item to a quest.** `C_QuestLog.GetQuestObjectives` has no item ID.
- **Quest log** (always on): item objectives matched by item **name**, parsed for both "Name: 0/1" and "0/1 Name" (which Forever uses is unverified). Retried on `QUEST_LOG_UPDATE` until names arrive. Quests in the log always count, finished objectives included.
- **QuestieDB** (`LibQuestieDB`, optional, contract 2+): quests not accepted yet. Its `Item.relatedQuests` holds about 13% of the pairs, so the module builds its own index from `objectives[3]`, `objectives[6]`, `requiredSourceItems` and `startedBy[3]`, in a coroutine at 3 ms a frame.
- **QuestieDB data shape:** baked into the TOC as base64 CBOR (grep finds nothing; use `LibQuestieDB.Quest.Get(id, "field")`). `objectives` is sparse, race masks exceed 2^32 (use arithmetic, not `bit.band`), and a bare classic faction mask (77 / 178) is compared with the toon's faction.
- **Upcoming quests (`UpcomingBlocker`):** not completed or hidden by Questie, not a holiday sort, right race and class, not repeatable, profession learned, no exclusive / later-chain quest done, takeable within `UPCOMING_LEVEL_WINDOW` (5) levels, not trivial, and an item-started quest needs that item. Without the level and trivial rules a level 23 toon gets the icon on about 400 items instead of 70.
- **Refresh:** `QUEST_ACCEPTED`, `QUEST_REMOVED`, `QUEST_TURNED_IN`, `PLAYER_LEVEL_UP`, 0.5 s later.
- **Settings:** `Icon.ShowQuestItems` (every window), `Icon.ShowUpcomingQuestItems`. **Export:** `[Quest Value]`.
- **In game:** one drink showed the icon in bags and at the BetterBags vendor; the rest is offline. Unverified: the objective text layout and the index build time.
- **Parked idea:** status icons on Questie's map pins. QuestieDB has no item rewards, and Questie has no public hook for pins.

## Auction Value

`CaerdonAuctionValue.lua`; `GetAuctionValueInfo()` always returns the full breakdown.

- **Statuses:** `auction` replaces `sellable`; `auctionGoods` marks trade goods with no status. Soulbound, bind-on-pickup, account-bound and quest items are never candidates.
- **Rule:** `profit = quantity * (price * 0.95 - vendorPrice) - deposit * depositRisk`; `required = clamp(vendorValue * margin, floor, 1g)`. Floor: `Icon.AuctionMinProfit`, `"auto"` (25c per level, minimum 1s) or copper as a string.
- **Rule sets by max stack size:** single item `depositRisk = 2`, `margin = 1`; stackable `depositRisk = 1`, `margin = 0.25`, and quantity is everything owned including the bank. `BAG_UPDATE_DELAYED` re-judges stackables and refreshes only when a verdict flips.
- **Price:** Auctionator's public API (`GetAuctionPriceByItemLink`, `GetAuctionAgeByItemLink`, `RegisterForDBUpdate`); older than 7 days is ignored. No sales data exists, so the price used is the lower of the last seen price and the 14-day median daily low (3+ days; from internal `Auctionator.Database:GetPriceHistory`, pcall'd).
- **Forever price keys:** gear below item level 168 is keyed by item ID alone, so random suffixes share one price.
- **Deposit:** unknown formula; starts at the larger of 1s or 15% of vendor price. `features/Auction.lua` records a sample when an item goes into the sell slot (`CaerdonAuctionData`).
- **Icon:** only in bags and bank (`displayInfo.auctionIcon`); elsewhere `auction` draws as `sellable` and `auctionGoods` draws nothing. `Auctioneer` atlas, else the gold coin.
- **Settings:** `Icon.ShowAuctionValue`, `Icon.AuctionMinProfit`. **Export:** `[Auction Value]`. **In game:** untested.

## Refresh

- `RefreshItems` (cache wipe, generation bump, debounced feature refresh) runs on `TRANSMOG_COLLECTION_UPDATED`, `TRANSMOG_COLLECTION_SOURCE_ADDED`, `..._SOURCE_REMOVED`, `TRANSMOG_COSMETIC_COLLECTION_SOURCE_ADDED`, and on equipment, equipment set and expansion changes.
- The export's `[Transmog Collection Events]` section lists the last 25 such events with the refresh generation. Use it for "the appearance was learned but the icon did not change".
- **What belongs to one copy is added after the cache lookup.** Openable, locked, readable, refundable and the combine statuses are facts about one copy of an item in its bag slot, and the status cache is per link. `GetCaerdonStatus` therefore caches the verdict as it stands before them and calls `GetCopyStatus` after the lookup, on every call, for an item in a bag slot. Cached together, a verdict first asked for outside the bags stood for the copy in the bags: a lockbox taken from the mail had no icon until the next refresh (seen on Forever), and two copies in different states shared one verdict. What an item's use spell says about combining follows from the link and is kept per link (`copySpellCache`), so a cache hit costs the slot's container and purchase info and no more.
- **A box's lock is read from its slot** (`IsBagSlotLocked`, `C_TooltipInfo.GetBagItem`), with the text compared on every line. The tooltip of the bare link says "Locked" for a lockbox whether or not this copy has been opened, and the line's type depends on the toon: `ErrorLine` (41) for a toon that cannot pick locks, a plain line (0) for a rogue. The general tooltip scan reads only the plain one, so it called every box openable on the first toon and locked, opened or not, on the second. Seen on Forever: locked on a hunter and a rogue, openable on the rogue once picked, the icon changing as the lock was picked. Retail not seen.
- A no-op `Refresh()` leaves the stale icon while the Debug Frame shows the right status. Still empty, untested: CargBags, Sorted. BaudBag keeps the buttons it was asked to draw, with their slot, and draws them again; Inventorian draws every button its two windows hold (both seen on Forever in the rotation: no button drawn again before, every one after; bags only, the bank not looked at). The test addon's rotation fails a bag feature whose buttons a full refresh does not draw again (notes: Test Addon).

## Integration Report

An integration hooks functions of another addon, and that addon can rename or remove them in any update. The feature then draws nothing and raises no error. The report says, per integration, whether the places it attaches to were there.

- **Declared and noted.** A feature that decorates another addon's frames has `Mixin.integration = { addon, hookPoints, optionalHookPoints }` and calls `self:NoteHookPoint(label, owner, key)` on the line before it attaches, with the table and key the hook itself uses (`FeatureMixin.lua`). `CaerdonIntegrations.lua` reads the two: a point is found, missing (looked for, not a function), not reached (the code has not come to it) or undeclared.
- **Verdict per integration:** `problem` when a needed point is missing, the feature's `Init` did not finish, or a note has no declaration; `waiting` while a needed point has not been reached; `ok` otherwise. The Debug Frame export prints one line per integration under `[Integrations]`, with the other addon's version, so a user's report carries it.
- **Note where the code attaches, not where it looks things up.** A lookup that raises (`GetAddon`, `GetModule`) shows as an `Init` that did not finish. A point behind a window (the Narcissus set frame, the buttons of Baganator and of BetterBags' vendor, Inventorian's `OnEnable`) is noted when it is reached, and reads "not reached yet" until that window has been opened.
- **The note changes nothing.** It never raises, whatever the other addon hands over, and it does not replace the guard or the hook beside it: an `Init` that raised an error before still raises it.
- **A message is only half proven.** For a subscription (`RegisterMessage`) the note shows that the registering function exists, not that the other addon still sends that message. A draw shows that; the test addon counts draws per feature.
- **A callback the other addon calls by name** has nothing to look for beforehand: `NoteHookCalled(label)` records the call arriving (Venture Plan's `VPEX_OnUIObjectCreated`).
- **Listed:** only integrations whose addon was loaded before this one; the others never register a feature.
- **KkthnxUI and NDui** report their hook point as missing while that UI's own bags are switched off: there is nothing to decorate.
- **Evidence:** every integration was run offline against a stub of its addon, and installs the same hooks as before the notes were added. The declared names were found in the installed source of BetterBags 0.9.3, Auctionator 347, Dialogue UI 1.0.7, Narcissus 1.8.7, Angrier World Quests and Venture Plan 8.1.6. Forever client (1.60.1.70938): the export's section and the records show every point found for Auctionator, the three BetterBags features and Dialogue UI, with draws for BetterBags' bags and vendor. Narcissus finds its set frame and slot buttons at login and reaches the set buttons only once a set is shown. Retail has not been seen, and the other integrations cannot be run here.

## Dialogue UI

`external/DialogueUI/Core.DialogueUI.lua`. Dialogue UI shows a quest at an NPC in its own window (`DUIQuestFrame`) in place of Blizzard's quest frame; the quest log and the map's quest details stay with the QuestLog feature.

- **Hooks:** `hooksecurefunc` on the global `DUIDialogItemButtonMixin`, for `SetItem` (every item draw) and `OnRelease` (back to the pool). The button template copies the mixin when a button is created, and the first button is created for the first quest shown, so the table hook reaches all of them. That needs Dialogue UI loaded first: it is in `OptionalDeps`.
- **What a button shows** is in Dialogue UI's own fields: `objectType` ("item", "currency", "spell", ...), `type` ("reward", "choice", "required") and `index`. The link is `GetQuestItemLink(type, index)`, the tooltip `C_TooltipInfo.GetQuestItem`.
- **Drawn:** reward and choice items. Not drawn: required items (handed in, not received) and currencies (only retail renown currencies have a status, and that path is unverified).
- **Tracking (`trackedButtons`):** what was last sent to the core per button: the link, plus whether Dialogue UI's own upgrade arrow was on the button. Dialogue UI sets a button again every 0.05 s while it waits for the item's name, so an unchanged draw is skipped; `Refresh()` forgets the links and re-runs every tracked button. A released button also loses its button state (`ClearButtonState`), so a request still on its way for it is dropped instead of drawn on a pooled button.
- **Display rules** are the QuestLog feature's (`GetDisplayInfo` is passed on), so "Quest rewards" on the Icons page covers both.
- **Placement (author decision, fixed layout):** Dialogue UI has a marker of its own for three corners of the icon: its upgrade arrow at the bottom left, the highest sell price coin at the top left (its option, off by default), and a red "!" at the top right for an item the toon cannot use (part of its `ItemOverlay` texture, no option, about 15 px, centered 6.8 / 7 px in from the top right corner of `AreaDefinitionItemBorder`). The overlay sits on that 36 px frame and the icon goes exactly over the "!" (`overrideStatusPosition` TOPRIGHT, `ALERT_INSET_X` / `_Y`), for every status: an icon only shows on an unusable item when there is still something to learn, which says more than "cannot use", and two markers side by side read as a disagreement. Size is `GetSlotStatusSize`; the ring of an important icon covers the "!", a minor icon (0.8 of it) may leave a rim. Text is fixed at the bottom, the level gain at the bottom right. The player's layout does not apply (`GetLayoutNote` says so in the layout editor).
- **One upgrade arrow (author decision):** where Dialogue UI has put its arrow on a button (`button:DoesButtonHaveMarker("upgrade")`; its "Evaluate Item Rewards" option, Pawn's verdict where Pawn is installed), `GetDisplayInfo` switches `upgradeIcon` and `levelGain` off, so this addon draws no arrow, no badge and no level gain there. Any other icon stays. The arrow can arrive 0.33 s after the item, so `ShowUpgradeIcon` is hooked too and draws the button again. An upgrade only this addon sees keeps its arrow and gain. `displayInfo.levelGain` exists for this; no other feature sets it.
- **Light background:** parchment shows beside the icon, so the buttons pass `roundStatusIcon` (see Icon Size and Placement).
- **Planned sell icon:** a sell icon on the best paying choice would mean what Dialogue UI's coin means, so it has to yield to the coin the way the arrow does. The coin sets no marker on the button; its frame would have to be found among the button's children.
- **Setting (author decision):** `Icon.ShowOnDialogueUI`, "Show icons on its quest rewards" in a Dialogue UI section of the Display page, only offered while Dialogue UI is loaded. Off clears every reward button and draws nothing there; the buttons stay tracked (`SWITCHED_OFF`), so `Refresh()` draws them again when it is switched back on. It is a whole-window switch because the window is another addon's, with markers of its own; which icons show while it is on still follows "Quest rewards" on the Icons page. Checked in game.
- **Debug keybind:** the button carries `caerdonDebugItemLink`; Dialogue UI's own tooltip is not one `GetHoveredItemContext` knows.
- **Tooltip line:** only with Dialogue UI's "Use Blizzard Tooltip" on; its own tooltip gets none.
- **Not covered:** the reward popup after a turn-in (`QuestFlyout`) and the looted quest item popup.
- **In game:** confirmed for reward choices: the icons, the circle clip and the upgrade arrow standing down. Not seen yet: the fixed layout over the "!", the level gain standing down, text on a reward, a minor icon over the "!".

## Icon Size and Placement

- **Reference look (author decision):** the default Blizzard slot. Important icon 20/37 of the short side of the frame it sits on, minor icon 0.8 of that, center a fifth of the icon's size in from the corner. `GetSlotStatusSize(width, height, noMaximum)` returns it, clamped to 13..24 px. Bag addons whose slot size the player sets pass `noMaximum`.
- **Windows opt in** by passing `statusProminentSize`; the core does not apply the rule by itself. Moved: BetterBags, quest rewards, Dialogue UI's reward buttons, Auctionator, dressing room outfit rows and set buttons, the item conversion output slot, the dungeon journal's search preview. Already at the value: the auction sell slot, crafting order browse rows. Deliberately not moved: the round output button of the profession window and of the crafting order form (fixed 20 px), Narcissus' round dressing room slots, world quest pins and the dungeon journal's lists and suggested reward (below).
- **Not measured, so still on their old values:** loot rolls, and what needs retail content: the dungeon journal's item sets (the tab was disabled in 12.1.5), mission rewards (covenant table, landing page report), Great Vault, Black Market (rows, hot deal). They follow the player's layout; the mission inset was made for the top left corner. Blizzard's guild bank is a 37 px slot with no options of its own, so it is the reference look; only its room has not been measured (BetterBags hides that window).
- **Measured (retail 12.1.5, default icon layout):**
  - World quest pin: a 20 px button whose art (`NormalTexture`) is a 32 px circle around it. The 15 px icon, 10 px in, lies inside the circle. The slot look would put the icon's center outside it, so the inset stays.
  - Dungeon journal loot row: a 42 px icon 2 px in from the list's clipping edge. The 8 / 7 inset lets a 20 px icon hang out by exactly those 2 px, and on a right-hand anchor keeps it off the item's name; the slot look would hang 6.8 px. The rows pass `keepInsideWhenClipped` for an icon the player has made bigger: at 100% the icon stays where it was (seen in game), the move inside has not been seen.
  - Dungeon journal search result row: a 36 x 35 px icon with 11 px of room, so the slot look would fit. It shares the loot rows' inset so both lists of the journal look alike (open: author's call).
  - Dungeon journal search preview: a 19 x 18 px icon, nothing clipping it. It had 13 px at 2 / 2 and now gets the slot look, which is the same size 0.6 px further in.
  - Dungeon journal suggested reward: a 30 px icon in a ring (`adventureguide-rewardring`), no mask reported, taken as round. The 8 / 7 inset keeps the 20 px icon's center on it.
  - Dressing room set button: a 24 px icon in a 32 px row with 16 px of room. It had 13 px at 1 / 1 and now gets the slot look, the same size 1.6 px further in.
  - Crafting order form output: 47 px with a circle mask, the profession window's output button. Left on the 20 px default like that one.
  - Item conversion output: a 48 px square slot, unmasked, nothing clipping it. It had the 20 px default and now gets 24.
  - Crafting order browse row: 20 px tall, 13 px icon anchored LEFT hanging 3.5 px into 5 px of room.
- **Measured (Forever, button units, important / minor):** Blizzard bags, bank, vendor, mail and loot are 37 px slots with a 20 / 16 px icon that hangs 6 / 4.8 px outside the corner. Auction and profession rows are 20 px tall with a 13 px icon and no icon region. Every slot window had at least 10 px of room around it; only auction rows have none.
- **Clip-aware placement (`options.keepInsideWhenClipped`; BetterBags, Auctionator, dungeon journal lists):** `RunClipPass` (0.1 s after the draw) finds the nearest clipping parent and, when its room on the anchor's side is less than the overhang, re-places every icon in that frame inside the corner at `CLIP_INSIDE_SCALE` (0.8). The answer is per clipping frame and looked up on every draw, because pooled buttons move between grids. Only horizontal room decides. The full size is kept on the icon (`caerdonBaseSize`) so it never shrinks twice. Confirmed in game for BetterBags' two designs.
- **Button geometry recorder (`CaerdonButtonGeometry.lua`):** with **Enable debug** on, `ProcessItem` notes every button it draws and one per window and option set is measured 0.2 s later (up to 6 shapes per window, session-wide; a button whose width follows its text makes a shape per width). A button with no layout is looked at again three times, a second apart, and the export then says why a shape was never measured. The export's `[Button Geometry]` section prints the player's layout (and whether it is the default: it is part of every number in a window that is not hand-fitted), then per shape options, size, what the overlay sits on, masks, the icon's size and overhang, text, stack count reach, and the nearest clipping parent with its room. `/cdebug geometry` shows only that section.
- **Ring icons on a light background (`options.roundStatusIcon`; Dialogue UI):** the store's category icons (`SetRingIcon`: star, "?", bag, key, ...) are a ring in the middle half of a 64 px texture with a dark shadow around it. The crop to the ring's square keeps the shadow in the corners: lost on a dark slot, a square that turns with the animation on parchment. The option clips the icon to the ring (`TempPortraitAlphaMask` on `mogStatus`, `RING_ICON_CLIP` = 0.9 of its size; the ring measures 0.88, and `SetStatusIconPosition` sizes the mask). No rim of shadow may be left: it is a drop shadow, heavier below, so a rim swings around as the icon turns. Opt-in because the mask's fit is only seen in game and Baganator re-parents the icon. Blizzard's quest frame is parchment too and has not been looked at.
- **Rectangles are not shapes.** The round profession button read as a 47 px slot. A mask does not mean round either: the two masks of `ItemButtonTemplate.xml` are named in the export (`TempPortraitAlphaMask` is the circle, `common-iconmask` every standard slot).
- The copy dialog is a child of the Debug Frame, so anything that shows it opens the Debug Frame first. Its edit box must not use `SetSpacing`; that broke the selection highlight.

## Settings

Two sub-pages under "Caerdon Wardrobe": **Icons** (`config/Icons.lua`) and **Display** (`config/Display.lua`), built with the helpers in `config/ConfigPanel.lua`.

- **Icons page:** one block per icon: the real texture, what it means, where it shows, then its rules. Everything not about an icon (corner, animation, text, vendor gray-out, tooltip line, debug) is on Display.
- **Learnable by this toon (`ownIcon`):** toggles only for bags and bank, guild bank, vendor and auction house (`Icon.ShowLearnable.*`). Every other window always shows it.
- **Learning for another toon (`otherIcon`):** one key per window in `Icon.ShowLearnableByOther`, read with `~= false`. World map, missions, Great Vault and item conversion have no option. Windows a client does not have are left out (`IsWindowAddOnAvailable`, with `Blizzard_GuildBankUI` as a canary).
- **Quest icon:** `Icon.ShowQuestItems` is one switch for every window.
- **Helpers:** `AddTitle`, `AddIconHeader`, `AddSection`, `AddLabel`, `AddCheckbox`, `AddCheckboxGrid`, `AddAllNoneButtons`, `AddDropdown`, `AddButton`, `FinishLayout`. Widths are fixed pixels (the canvas is about 640 wide). An option is `{ key, text, tooltip, configSection, configSubsection, configValue }`; `key` becomes the global `CaerdonWardrobe<key>` and must be unique across both pages. `dependsOn` grays a control out.
- **Values** are resolved from `CaerdonWardrobeConfig` on every read and write: the table is replaced on a version bump, a missing section is created on write, nil reads as the default. Pages set `frame.OnRefresh`, which the settings window calls on every display; a page's first display is not an `OnShow`.
- **Main page** (`config/Config.lua`, `Config.xml`): a short description and the support box, no options. The box sizes itself from its text (`FitCard`), because the sentence wraps with the page's width.
- **`/caerdon`** (`NS:OpenSettings`) opens the main page, as does the dialog's button (author decision). It does nothing in combat.
- **Category ID:** the main category keeps the numeric ID it was created with and is kept in `NS.SettingsCategory`, which the sub-pages register under. Do not set `category.ID` to the addon's name (the old way to make `Settings.GetCategory(name)` work): `Settings.OpenToCategory` hands the ID to `C_SettingsUtil.OpenSettingsPanel`, which raises an error for anything but a number (seen on Forever).
- **Dialog text:** a slash command at the end of a line is wrapped after the slash (seen on Forever), so the footer starts with it.
- **One-time message dialog** (`MESSAGES` in `config/Config.lua`): a `StaticPopup` with **Open Settings** (`NS:OpenSettings`) and **Close**. `CaerdonWardrobeConfig.MessageSeen` is the number of the last entry shown.
  - Settings saved before the field existed read as 0 and get the latest entry. A fresh install starts at the latest number and gets the welcome text; settings reset by a `Version` bump get the reset text.
  - Only the latest entry is shown, once per account. It comes up a few seconds after login, waits for the end of combat (the button cannot open the settings during it), and counts as seen once it is on screen. Add an entry at the end and never renumber.
  - A dialog interrupts, so add an entry only when players will see different icons or need to revisit their settings (author decision): a sentence or two, not release notes.
- **In game:** the pages were built against mocked frames; real text widths and wrapping are unverified. The main page's box and the dialog (its look, its timing after login) are offline only.

### Layout settings

Where the icon, the binding text, a gear set's name and the level gain sit, and how big they are.

- **Keys:** `Icon.Position / Scale / OffsetX / OffsetY`; `Binding.*`; `Binding.GearSet.*`; `Icon.UpgradeDelta.*`. Positions are the nine anchor names, scales are percentages, offsets a nudge right / up in pixels.
- **Relative to the window's own values:** size is a factor on `statusProminentSize` / `bindingScale`, the nudge is added to the window's inset. `GetStatusBaseSize(options)` is the one place the icon size comes from.
- **Hand-fitted windows** (`overrideStatusPosition` / `overrideBindingPosition`, or `fixedLayout = true`) get no size factor and no nudge. `fixedLayout` rows still follow the player's anchor.
- **Inset** only applies along an axis where the anchor is on an edge.
- **Scaled text:** `SetPoint` offsets of a region with `SetScale` are in its own units, so default spacing is divided by the player's scale.
- **Text and the level gain on one row (author decision):** a part goes where the player puts it and the gain never moves. Text that would run into the gain moves away by the gain's height, as it does for a stack count (`bindingTextMovedFor` says which). The gain's inset is `LEVEL_GAIN_INSET` (4 px).
- **Samples measure text at normal scale** (`options.sample`), because a string's width in its own units depends on the scale it is drawn at.
- **Defaults reproduce the previous look.** The binding text's default position stays Bottom (author decision).

## Layout Editor

`config/LayoutEditor.lua` (`CaerdonWardrobeLayoutEditor`, `/caerdonlayout`), opened from the Display page.

- **The examples are real** `ItemButton`s decorated by the drawing code with a made-up status (item: Hearthstone 6948), so they cannot drift from it. The large slot is a 37 px slot in a frame with `SetScale(4)`.
- **The editor mirrors the settings (author decision):** a part switched off everywhere is not drawn and has no button; an example only about such a part is left out (`EnabledParts()`, `TEMPLATES[...].needs`). Parts are switched on and off on the Icons page, never in the editor.
- **A gear set's name is a part of its own** with a full layout, independent of the binding text's.
- **Controls:** pick a part, nine anchor squares, a size stepper (5% steps, 50 to 300), a one-pixel nudge cross (up to 40), "Reset this part", "Reset everything", "Undo changes" (back to the snapshot taken on open).
- **Changes are written live.** Done keeps. Any other close with changes shows `CAERDON_LAYOUT_KEEP_CHANGES` (Keep, Discard, Keep editing); only a click on Discard restores the snapshot.
- **Samples cut to "B...":** a slot drawn while its page is hidden has no width yet, so `RedrawSamples` queues one more redraw 0.05 s later.
- **Addons that place things themselves:** a feature may define `GetLayoutNote()` returning a sentence that starts with the addon's name and a colon, plus an optional button. They show as a callout at the top of the editor; a note leads with what does not work there. Baganator's button opens its settings on the Icons tab (`OpenBaganatorIconSettings`: its `ShowCustomise` event toggles the window and always selects Theme, so the tab is set on the dialog itself).
- **Not built:** samples on the player's real windows; a stand-in for the player's own bag addon's slot.
- **In game:** the callout and Baganator's button are confirmed; the window's overall layout was built against mocked frames.

## Processing Pipeline

- **One pending request per button.** `UpdateButton()` queues into `waitingToProcess` under the button, and the request carries its location key (`GetRequestKey`: feature and bag slot, or the feature's own key). The key still decides whether a request is current: it is dropped when the button has since been asked for another location. The lists used to be indexed by the location key, so of two buttons of one feature showing the same slot only the one asked for last was drawn: BetterBags' food and drink bar shows two bag items a second time, and after every refresh one button of each pair kept its old icon (seen on Forever with the test addon's rotation, 2 of 47). `pendingTooltipRetries` and the `ContinuableContainer` list are per button for the same reason, and a request coming back from the container never replaces a newer one for its button. Seen on Forever: with the change BetterBags draws all 47 again, a bags snapshot taken before and after has nothing changed, and no stop of the rotation shows anything differently. Retail not seen.
- `ProcessItem_Coroutine` (via `OnUpdate` every 50 ms) moves them to `processQueue`, which is reset at coroutine start.
- Items where `IsItemDataCached()` is false (it needs `IsItemCached()` and `customDataLoaded`) take a `ContinuableContainer` path, whose callbacks route back through `waitingToProcess`.
- **Not-ready retries:** when the tooltip still reads "Retrieving item information", `ProcessItem` stashes the request in `pendingTooltipRetries` and one 1 s timer re-runs them. The limit (`NOT_READY_MAX_RETRIES`, 10) is counted per button in `buttonState`. The timer only retries while the button still has the same location key and item ID. `GetRequestKey` builds the key for both paths.
- **`GetDisplayInfo` gets the host's button** in both draws (status icon and binding text), for a feature whose answer depends on what the host addon has put on it.
- **Overlay:** `EnsureCaerdonButton()` creates a child frame with `SetAllPoints`, holding `mogStatus` textures, `bindsOnText` and `upgradeDeltaText`. `buttonState` has weak keys.
- **Binding text:** with `bindingScale < 1` the font string width is divided by the scale; scale is reset to 1 before `GetStringWidth()`.

## Dressing Room

- `TryHookDressUp()` installs hooks in independent groups, because the globals load from different addons (`DressUpFrameTransmogSetButtonMixin`, `DressUpFrame`, `DressUpOutfitDetailsSlotMixin`); `ADDON_LOADED` retries until all are in. `hooksecurefunc` on a mixin table works for ScrollBox buttons, since `Mixin()` copies the hooked function.
- Items in the SetSelectionPanel are Equipment. `UpdateSetSelectionButton` sets `extraData.appearanceSourceID` from `elementData.itemModifiedAppearanceID`.

## LoadSources

`waitingForItems` is keyed by item ID, so `#waitingForItems == 0` is always true and `callbackFunction()` fires immediately; real completion is handled by `ProcessTheItem` / `FailTheItem` with `not next(waitingForItems)`.

- **Leave it.** Switching to `not next(...)` makes `LoadSources` block the whole `ContinuableContainer`, and every ensemble in the batch then shows as unlearnable.
- **Consequence:** completion is reported twice, so `CaerdonItemMixin:ContinueWithCancelOnItemLoad` wraps its callback to fire once. Blizzard's `ContinuableContainer` crashes on a late duplicate (`bad argument #1 to 'ipairs'`), which surfaced on a fresh Forever install. `ContinueOnItemLoad` is deliberately unguarded: features rely on the re-run.
